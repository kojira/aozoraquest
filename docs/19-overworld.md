# あおぞらワールド (2D オーバーワールド) 仕様書案

status: **draft v2 — 主要判断済み** (2026-07-17 オーナー回答反映)。細部は実装 PR で詰める。

ブルスコンの試練 (docs/18) を「メニューから挑む」形から、**2D の広域マップを
一歩ずつ探索する**形へ拡張する。移動・遭遇・採集・街での買い物をゲームループの
中心に置き、戦闘は docs/18 のエンジン (v2: MP/ため予告/やくそう) をそのまま使う。

## 1. ワールド

- **大きさ**: 1024 × 1024 タイル。**トーラス** (端は逆の端に接続。x, y とも mod 1024)。
- **生成**: 固定のグローバルシードから**決定的に手続き生成** (packages/core に純関数
  `tileAt(x, y): Terrain`)。全ユーザーが同じ世界を見る。1M タイルを保存しない —
  表示のたびに計算する (16×16 = 256 タイル/画面なので計算コストは無視できる)。
  - ノイズは**周期格子** (格子点 index を mod 1024) で作り、トーラスで継ぎ目が出ない
    ようにする。標高 + 湿度の 2 チャンネル + バイオーム規則で地形を決める。
- **地形** (8 種):

  | 地形 | 通行 | 遭遇率/歩 | アイテム率/歩 | 備考 |
  |---|---|---|---|---|
  | 平地 | ○ | 低 (5%) | 3% | 基本地形 |
  | 林 | ○ | 中 (10%) | 5% | |
  | 森 | ○ | **高 (20%)** | 8% | 実入りも危険も大きい |
  | 池 | ✕ | - | - | 将来: カヌー/船で通行可 |
  | 川・海 | ✕ | - | - | 将来: 船で通行可 |
  | **橋** | ○ | 低 (5%) | - | 幅 1〜3 タイルの川に「スパン」として決定的に配置 (間隔 ~24)。それより広い水域 = 海 (船で渡る) |
  | 山 | ✕ | - | - | 将来: 飛行船で通行可 |
  | 街 | ○ | 0 | - | なんでも屋。安全地帯。平地の上に描画 |

  タイルのビジュアル案は `docs/overworld-drafts/tiles.html` (SVG、v2 でオーナー確認)。
  未踏は「霧」(雲がかった青灰) で表現。**プレイヤーはユーザーの実アバター +
  ジョブ装備 (components/job-equipment.tsx) をマップ上にそのまま描画**する。

  (率は初期値。BATTLE_TUNING 同様に WORLD_TUNING として core に集約し調整可能に)
- **街**: 128×128 の各リージョン (8×8 = 64 個) に 1 つ、平地の上に決定的に配置
  (海主体のリージョンには無し。生成ドラフトでは 53 街)。初期位置は
  **メイン大陸 (最大の徒歩到達成分) 内の街**とする。
- **到達可能性の保証** (PR-W1 のテストで固定): 開始の街から徒歩+橋で歩行可能タイルの
  **95% 以上**に到達できること (生成ドラフト実測 98.2%、街 49/53)。
  - 徒歩到達できない飛び地は**意図的な後期コンテンツ**: 島の街 (船で解禁)、
    山に囲まれた中央山塊内の秘境 (飛行船で解禁) → **魔王の城の配置候補**
    (オーナー案 2026-07-17)。
- **地域性**: リージョンごとに**危険度** (原点からのトーラス距離 + ノイズ) を持ち、
  出現モンスターの tier とプールが変わる。バイオーム別テーブル
  (森=植物/獣系、水辺=大蛇、山麓=ゴーレム、夜鴉・鬼・竜は高危険度のみ、など)。
  モンスター図鑑は既存 9 種から始め、地域固有種を追って足す。

## 2. 画面と移動

- **ビューポート**: 16×16 タイルのみ表示 (プレイヤー中央固定、世界がスクロール)。
  モバイル幅 ~360px で 1 タイル ~22px。描画は SVG (絵文字/簡易シンボル + 色) で軽量に。
- **移動**: 1 タップ = 1 マス (十字キー UI + スワイプ)。トーラスなので座標は自動 wrap。
- **未踏の霧**: 訪れたタイル + 現在のビューポートのみ描画。
  **地図のかけら**を入手すると、そのリージョン (128×128) の俯瞰ミニマップが解禁される
  (実装はリージョン番号の整数配列 — 64bit ビットフィールドは JSON/atproto に安全に
  載らないため。最大 64 要素で有界)。かけらは移動時の発見物 or
  戦闘勝利ドロップ (低確率) で入手。

## 3. 経済 (オーナー決定済み)

- **移動コスト: 1 歩 = 1 あおぞらパワー** (決定 2026-07-17)。「1 日 100 投稿する人は
  ザラに居る」= ヘビーユーザーほど遠くまで歩ける設計。投稿がそのまま行動力になる。
- **なんでも屋** (街の上で開ける): あおぞらパワー + 素材で購入。
  - **品揃えは街ごとに違う** (決定)。基本は「その街の周辺リージョンに出る
    モンスターに効く装備」を売る = 地域のモンスターと店がセットで意味を持つ。
    装備には**特効** (species / バイオーム別のダメージ補正) を持たせる。
  - **武器/防具**: 戦闘値に加算 (atk/def/agi/int/luk への補正) + 特効。装備レコードは
    `app.aozoraquest.equipment/self` に保存。docs/18 Step2 の実現。
  - **道具**: やくそう (素材ドロップの補完)、地図のかけら、将来はカヌー/船/飛行船。
- gamble 系ジョブ (低 atk・低 int) は装備で火力を補う前提 (docs/18 の既知課題の回収先)。

### 街の名前

64 の街すべてに固有名を付ける (決定)。core に日本語の名前テーブルを持ち、
リージョン番号 → 名前を固定対応 (例: 「そらみの街」「かぜまちの宿場」「しおさいの湊」…)。
バイオーム/危険度に合わせた命名 (水辺は湊・岬、森は杜・木立、高危険度は砦・関 等) で
世界の手触りを出す。名前はミニマップ・街画面・店のヘッダに表示。

## 4. 不正防止 — Worker 乱数オラクル

遭遇・アイテム発見・(そこから始まる) 戦闘のシードを**クライアントに選ばせない**。

- **方針: 移動も戦闘もサーバー権威** (オーナー決定 2026-07-17)。クライアントは
  入力 (移動方向 / 戦闘コマンド) を送るだけの薄いレンダラーで、判定はすべて
  Worker が行う。バトルエンジンは packages/core の**純関数** (seed 決定的・state は
  JSON 化可能) として実装済みなので、**Worker が同じ core を import してサーバー側で
  resolveTurn を実行する** (web と worker のコード共有 = ロジックの二重実装なし)。
- **構成**: 既存の Cloudflare Worker (アプリ配信) に `/api/world/*` を追加。
  per-DID の **Durable Object** が歩数カウンタ・現在位置・進行中の BattleState を保持。
- **移動プロトコル** (**1 歩 = 1 リクエスト**。シードのまとめ発行 (バッチ) は、先読みで
  「次の歩の遭遇が事前に分かる → 止まって回避」というチートを許すため**採らない**):
  1. クライアント: `POST /api/world/step { dir }`
  2. Worker (DO): 位置は DO 側が正。歩数カウンタを進め `seed = HMAC(secret, did|counter)`
     を生成し、地形 (`tileAt`) と遭遇/アイテム判定をサーバー側で解決。
     結果イベント (遭遇開始 / アイテム入手 / 何もなし) と新しい座標を返す。
- **戦闘プロトコル** (遭遇したら DO が BattleState を保持し、**コマンドを毎ターン送る**):
  1. クライアント: `POST /api/world/battle { command }` (たたかう/とくぎ/ぼうぎょ/やくそう)
  2. Worker (DO): 保持中の BattleState に resolveTurn を適用し、表示用の
     イベントログ + HP/MP/残やくそう + outcome を返す。**クライアント側では戦闘を
     解決しない** (コマンド選択の結果を偽れない)。
  3. 決着時: Worker が**署名付きの結果** (outcome / drops / XP / counter) を返し、
     クライアントはそれを battle レコード (PDS) に保存 → 勝敗・ドロップの改竄不可、
     後から検証可能。
  - レイテンシ (エッジで ~50-150ms) は移動アニメ・戦闘演出の楽観表示で隠す
    (通行可否はクライアントも `tileAt` で事前計算できる)。
- **担保されること**: シードの先読み・引き直し不可、遭遇回避・戦闘結果・ドロップの
  改竄不可、位置の改竄不可。**担保しないこと**: 見た目だけの改造 (報酬に繋がらない)。
- 位置・歩数・所持は PDS レコード (`app.aozoraquest.world/self`) にも保存し、
  Worker の counter と突合できるようにする (監査線)。

## 5. データ (PDS)

| record | rkey | 内容 |
|---|---|---|
| `world` | self | x, y, 歩数残 (案A の両替分), 解禁リージョン bitfield, 乗り物フラグ |
| `equipment` | self | 装備中の武器/防具/道具 |
| `purchase` | tid | 購入履歴 (パワー消費の記帳。cardDraw/battle と同型) |
| `battle` | tid | 既存 + `worldSeedSig` (Worker 署名) を追加 |
| `pickup` | tid | フィールド採集の記帳 (item, 座標, seed, 署名) |

パワー式は `viaPosts − userMessages − cardDraws − battles − purchases − steps両替` に拡張。

## 6. 試練 (現行) との関係

- /spirit の「試練の間」は**ワールドへの入口**に置き換える (ブルスコンが案内役)。
- 遭遇戦闘は現行エンジンをそのまま使用 (コマンド/MP/やくそう/そらのしずく/にげる/
  ため予告は不変)。敵 tier は「選ぶ」のではなく**地域で決まる** (難易度自動化の完成形)。
- **野外戦闘は試練と同じ機構で本物の支払いと報酬を持つ** (2026-07-17 更新。
  オーナー要望「報酬も出るようにしてほしい」): 遭遇成立時に battle 仮レコード +
  `battles` カウンタ増分 (1 戦 = パワー 1)、決着で確定レコード + XP + 素材ドロップ。
  **パワー残高が 1 未満のときは遭遇しない** (散歩は無料のまま、無料戦闘で報酬だけ
  稼げる穴を作らない)。遭遇判定そのものは引き続きプレビュー (Math.random) で、
  W3 で署名付き seed に置換する。
- **敗北時は「最後に立ち寄った街」に戻される** (2026-07-17 更新。最寄りだと未訪問の
  街に飛んでしまうため)。まだ街に入っていなければ、はじまりの街。追加のデスペナは
  無し (消費済みパワーと歩いた分が実質のコスト)。
- **エンカウント演出** (オーナー要望 2026-07-17「演出はすごい大事」): 遭遇時は
  DQ1 オマージュのワイプ (黒い四角が中心から回転しながら画面を埋める → 覆い切ったら
  バトル画面に切り替えて逆再生で開く。encounter-wipe.tsx)。支払い通信が長いときは
  全面黒で hold してつなぐ (= 通信待ちが演出に化ける)。試練の開始にも同じ演出。
  prefers-reduced-motion では実質即時切替。
- **HP/MP は戦闘をまたいで持続する** (決定 2026-07-17)。回復手段: 街に入ると全回復
  (宿) / やくそう = HP、そらのしずく = MP (どちらも戦闘中もフィールドでも使える)。
  フィールドでの使用分はまだ記録されない (セッション内のみ。在庫の正を DO に移す
  W3 の申し送り事項)。**戦闘中の MP 自然回復は `JOB_MP_TRAITS` を持つジョブだけ**
  — 一覧と現行値は docs/18 §バトルエンジン (撤去済み doc だが `JOB_MP_TRAITS` の
  記述は現行仕様)。パラディンだけ「ときどき +1」の確率発動 (#564)。
  レベルアップでも HP/MP は全回復する (#547)。

### 本番リリース前の必須要件 (オーナー指示 2026-07-17)

以下がすべて揃うまで本番リリースはしない (プレビューの実機フィードバックより):

1. **移動のパワー消費** (1 歩 = 1 パワー) — W3 のサーバー権威化とセット
2. **仮想スティック操作** — 十字キーはスマホで操作しづらい。マップ上のオーバーレイで
   タップ + ドラッグ操作
3. **地図確認機能** — 地図がないとどこに街があるか分からない (W5 前倒し)
4. **街に戻るアイテム** — 「そらのはね」実装済み (2026-07-17)。最後に立ち寄った街
   (無ければはじまりの街) へワイプ演出つきで帰還。フィールド専用。当面の入手は
   飛行系モンスターのドロップ (コウモリ 0.12 / おおガラス 0.25)、W6 で全店の
   基本枠に安価で並べる。(開発用の位置リセットボタンは廃止済み)
5. **街ごとに特色のある品揃えのなんでも屋** — 移動する動機の核 (W6。設計は
   docs/20-shop-equipment.md)
6. **アイテムの調整**

### 実装記録 (プレビュー期)

- **橋の修正 (2026-07-17)**: 初版の橋は 20 スパン中 19 が「海岸の切れ込みを跨ぐだけで
  両端が同じ陸地」の飾りだった (オーナー報告「発見した全ての橋が全く機能していない」)。
  生成に局所連結チェック (半径 20 の陸上 BFS で回り込めるなら架けない) を追加し、
  bridgeMaxSpan 3→5。全 10 スパンが本物の渡河点になった (テストで固定)。
  橋タイルの移動に伴い、保存位置が歩行不能になったプレイヤーはロード時に
  最後の街へ退避する (通知つき)。なお橋は「半径 20 の迂回を省くショートカット」
  であり、大域連結は橋に依存しない (全橋を消しても到達率 97.4% / 到達可能な街
  49/53 は不変 — レビュー実測。船で渡る 4 街は将来コンテンツ)。
- ワールド画面のタイトルヘッダー削除・投稿 FAB 非表示 (/world)・一時メッセージの
  ボタン直下移動 (いずれもオーナー指示 2026-07-17)。
- **地図確認機能 (2026-07-17)**: 「地図がないとどこに街があるのか全く分からない」
  (リリース必須要件 #3)。どうぐ列の「🗺 ちず」ボタンで世界全図モーダル
  (1024×1024 を 4 タイルサンプリングした 256×256 canvas、初回 ~200ms で以降
  キャッシュ)。街 = 金ドット、現在地 = 点滅マーカー、タップで近くの街名を表示。
  プレビュー期は全図開示としていたが、「今全部見えちゃうのでリリースできない」
  (オーナー指摘 2026-07-18) を受けて W5 のかけら開示を実装済み (下記)。
- **ちずのかけら (W5、2026-07-18)**: 世界地図の開示範囲 = 解禁済みリージョン
  (world/self の `regions`、64 リージョン中)。**街に入るとその街の地方一帯
  (3×3 リージョン) のかけらを入手**し、地図がその範囲だけ広がる (通知一行つき)。
  未解禁リージョンはフォグで覆い、街・橋は描かずタップにも反応しない
  (「まだ ちずに ない ばしょだ。」)。新規プレイヤーは はじまりの街の 3×3 だけ
  開示された状態から (「開始の街でギルドから最初に必ずもらえる」の interim 実装 —
  W6e でギルドが narrative 上の入手元になる)。旧レコード (regions なし) は
  lastTown (無ければ現在地) の 3×3 でシードする移行措置。原設計の「移動時の
  発見物 / 戦闘ドロップでかけら入手」「訪れたタイル単位の霧」は未実装の拡張余地
  (リージョン単位の街入手が当面の正)。既知の割り切り: `regions` は world/self の
  置換保存に同居するため、**regions を知らない旧ビルド (PWA キャッシュ残り等) が
  保存するとフィールドごと消え、次回ロードで再シードされる** (= かけらが退行しうる)。
  複数端末の並行セッションでも同様 (レコード全体の LWW 保存のため、単調増加である
  はずの regions が片方の入手分だけ巻き戻りうる)。いずれも W3 で位置と一緒に DO へ
  正を移すことで解消する。regions はそれまでクライアント
  自己申告だが、開示されるのは情報のみで報酬に繋がらない (この実装以前は全員が
  全図を見えていた) ため、リリース阻害ではない。
- **つよさ画面 (2026-07-18)**: どうぐ列の「💪 つよさ」ボタンで全ステータス確認
  (オーナー要望「つよさコマンドでかっこよく全ステータスを確認」)。名前/ジョブ
  ジョブ Lv・HP/MP・たいりょく + 戦闘 5 ステータス (装備込み実効値 + 「そうび +N」内訳)・
  とくぎ/とくせい・そうび・次 Lv XP。表示値は戦闘に渡す playerCombatant と同一
  (「つよさの数字 = 戦闘の数字」)。issue #285 の第 1 項 (戦闘値の可視化) に対応。
  /me のレーダー (生の個人値) は #285 の別観点として継続。
- **仮想スティック (2026-07-17)**: 十字キーはスマホで非常に操作しづらい (オーナー
  報告) ため、マップ全面をタッチ領域とするフローティングスティックに置き換え。
  タッチ地点に基準リング + 指に追従するノブ、4 方向 (支配軸)、デッドゾーン 14px、
  歩調 170ms (方向転換は即時 1 歩)。十字キーボタンは撤去 (PC は矢印キー継続)。
- **そらのはね: 初期配布 + 行き先えらび (2026-07-18)**: オーナー要望
  「そらのはねは最初に 1 個もらう。過去に行ったことのある街を選択できるように」。
  冒険の初回に 1 個わたす (world/self の `gotStarterFeather` で二重配布防止)。
  使うと訪問済みの街 (`visitedTowns`、街に入るたび追加) から行き先を選ぶ FeatherModal
  を開く (今いる街は除外)。旧挙動 (常に最後の街へ) から「選べる」に変更。フィールド
  在庫はセッション内 (消費/初期配布の正は W3。フラグ自体は world レコードに永続)。
- **戦闘のマップ内化 (2026-07-18)**: 野外戦闘をページ遷移せず「暗転したマップ枠内」で
  行う (オーナー要望「戦闘もマップのサイズ上で全て解決し画面の遷移はしない」)。DQ1 風に
  上段 = マップ枠に重ねた暗転シーン (敵 + HP + ログ、`BattleScene`)、下段 = コマンド窓
  (`BattleCommands`) の 2 段構成。リザルトも同様 (`world-battle-result.tsx`)。BattleView は
  この 2 つを合成する薄いラッパに整理 (試練 trial-arena はページ全体を使うので BattleView
  を継続使用)。戦闘/リザルト中はマップ下の操作説明・notice を隠して縦スクロールをなくす。

## 6.4.5 プレイヤーの成長モデル (#518)

診断由来の 5 パラメータ (**合計 100 の比率**) は、そのまま戦闘値にはしない。**比率に
伸び率を掛ける**ことで、レベルを上げると実際に強くなるようにする。

```
ステータス = statFloor + 比率 × (statBase + statGrow × (Lv−1))   # atk/agi/int/luk
まもり     =             比率 × (defBase  + defGrow  × (Lv−1))   # def のみ伸びを抑える
たいりょく =             vit  × (statBase + statGrow × (Lv−1))
HP         = hpBase + たいりょく × 2      # DQ:「HP は体力の約 2 倍まで上昇」
MP         = mpBase + かしこさ × 1        # DQ:「かしこさが高いほど MP 上昇量が上がる」
```

- **たいりょく (`JobDefinition.vit`)** は診断の 5 パラメータとは**別枠のジョブ専用
  ゲームパラメータ**。体力は性格特性ではないので比率に混ぜず、ジョブの役割から手で
  設計する (守護者 45 〜 魔法使い/予言者 18)。ステータス画面では **HP の直下**に小さく添えて
  「HP がなぜその数字か」を見せる (せんとうのうりょくに並べると HP と離れて伝わらない)。
  HP を まもり 由来にしていた旧実装では「将軍が賢者より HP が低い」逆転が起きていた。
- **まもりだけ伸びを抑える**のは、**守備力は防具が主役**という DQ の構造に寄せるため
  (FC版〜「すばやさ÷2 + 防具」/ DQ3 HD-2D〜「みのまもり + 防具」— いずれも防具が大きい)。
  素のまもりが小さいので、たいりょくの高いジョブが HP と守備を二重取りしない。
  防具の def は **grade1 +5 / grade2 +15**。**grade3 の防具はまだ存在しない** (grade3 は
  職専用武器 `wp-<job>-high` だけにある) ので、現状の守備の上限は全職 grade2 の +15
  (たびのマント。全職が装備可)。上位帯の防具は #522 で追加する。
- **`statFloor`** は職ごとの比率差 (atk 7〜39 = 5.6 倍) が Lv1 で atk 1 対 8 に潰れ、減算式が
  低い側で 0 に沈むのを防ぐ下駄。DQ の Lv1 も「ちから + 武器」で全員が底上げを持つ。
  Lv50 では比率 × 2.65 に薄まるので職差は保たれる。**まもりには掛けない** (防具が主役の
  設計を薄めないため)。モンスターは防具を持たないので 5 ステとも掛ける。
- **`monsterStatFloor`** はモンスター側の下駄で `statFloor` とは**別の値**。ここが
  入口の難易度をほぼ 1 個で決めるので、独立して回せるようにしてある (§6.6)。
- **プレイヤーレベルは戦闘力に一切影響しない** (#507)。成長の単位はジョブレベルに一本化し、
  プレイヤー XP は加算せず、「ぼうけん Lv」の UI も撤去した (#508)。

### ダメージ 0 は正当な結果 (#518)

`minDamage = 0`。「攻撃力が低くても必ず 1 は通る」は**仕様の読み違い**で、メタル系の
identity (かいしんのいちげき か 特殊武器 でしか倒せない) を壊していた。DQ1/2 の式
`(攻撃力 − 守備力/2)` も攻撃力が守備力の半分を下回ると 0 になる。本作の
`atk × atkCoef(0.9) − def × defCoef(0.45)` も同じ 2:1 に揃えてある。

はぐれスライムには `flatDef = 255` (DQ2 のメタルスライム/はぐれメタルと同値) を与える。
これは **tier 倍率を通さない実効 def** で、どのレベルの相手にも identity が成立する
(最高の Lv50 将軍でも atk 108 < 127 なので通常攻撃は 0)。魔法無効 (`resistAllMagic`) も
最小 1 ではなく 0。

#### ただし 0 が許されるのは `ironDef` (メタル系) だけ — かすりダメージ

上の規則は**敵の identity のためのもので、プレイヤーが不死身になってよいという意味ではない**。
`minDamage = 0` は守る側がプレイヤーのときも同じように効くため、**装備 1 点で崖の向こう側に
届いてしまっていた**:

- grade2 の防具 (`まなびのローブ` def+15) を 1 つ着けると Lv5 の守備は 2 → 18
- tier1 のモンスターの**実効 atk は 5〜6** (`monsterStats` で `floor 4.3 + 素の値 × tier 係数`。
  素の値 7〜13 そのものではない) → `6 × 0.9 = 5.4 < 18 × 0.45 = 8.1` で **1 も通らない**
- 実測 (`sim:gear-early`): 被ダメ 0.00 / **無傷率 100%** = 一度も当たらない

そこで `MonsterDef.flatDef` を持つ敵にだけ `Combatant.ironDef` を立て、**この旗が無い相手に
対しては `攻撃力 × scratchRatio` を最低保証する** (「かすった」扱い)。

**床は減算の段階に置く** — `dmg = max(floor, atkTerm − defTerm) × roll`。乗算補正 (ぼうぎょ
半減・属性耐性・被ダメ軽減パッシブ) の**後**に `max` で入れると、0 沈み域でそれらが丸ごと
無効になり、**ぼうぎょすると被ダメが増える**逆転が 66 通り発生する (実測)。

##### 実測 (Lv5 賢者、レベルアップ全回復あり = 本番と同じ条件)

| | 変更前 | 変更後 |
|---|---|---|
| grade2 防具 tier1 の 1 戦あたり被ダメ | **0.00** | 0.49 |
| 同 無傷率 | **100%** | 60% |
| 同 tier2 連戦 (全職平均) | 47.6 戦 | **7.0 戦** |
| 素手 tier1 / tier2 連戦 (全職平均) | 39.7 / 5.0 戦 | 39.7 / 5.0 戦 (不変) |
| grade2 防具 tier3 連戦 (全職平均) | 0.9 戦 | 0.9 戦 (不変) |
| メタルへの通常攻撃 | 0 | **0 のまま** (`ironDef`) |
| ぼうぎょで被ダメが増える組み合わせ | 66 通り | **0 通り** |

床は減算が既に正のときは効かないので、**素手と tier3 は `scratchRatio` を動かしても 1 も
変わらない**。この値が効くのは「装備した低 tier」だけ。

##### 直っていない範囲 (意図的に別問題として残す)

**装備した Lv5 は tier1 では依然として死なない。** 1 戦あたり 0.49 しか削れないので、
レベルアップ全回復が入るとその削りは埋まってしまう (`sim:gear-early` の連戦は打ち切りに
張り付く)。ただし **1 戦 = あおぞらパワー 1、パワーは 1 投稿 = 1** なので、連戦数は
実際にはパワーが律速する (500 戦するには 500 投稿要る)。

「tier1 の街で grade2 の防具が買える (守備が 2 → 18 に跳ねる)」こと自体が本丸で、
これは**装備の段階を地域の危険度で区切る**話 = ワールド改善エピック P3。ダメージ式では
解けない (`scratchRatio` を 0.4 まで上げれば tier1 は有限になるが、tier2 が 3.9 戦まで
潰れて装備の意味が消える — 実測)。

## 6.4.6 XP の記録先は権威 state に一本化する (#534)

**ジョブ XP の正は `GameState.jobXp[archetype]` (管理者 PDS の権威レコード) だけ。**

XP が入るのは **投稿** と **戦闘** の 2 つだけ (オーナー判断 2026-07-27)。

**クエストの完了では XP が増えない。** デイリークエストも依頼クエストも同じ。
達成の判定は端末内 ONNX の分類に依存していて、**サーバーが同じ判定を再現できない** =
申告された額を検証する手段が原理的に無かった (1 投稿で 245 XP を申告できた)。
額を検証できないものは成長に効かせない、という線引きにした。

クエストは「今日は何を書くか」の道しるべとして残る。書けば投稿ぶんの XP は入る。

以前は 3 箇所に分かれていて、場所ごとに違う組み合わせを合算していた:

| 出所 | 旧・保存場所 |
|---|---|
| 投稿・診断・デイリークエスト | `analysis.jobLevel.xp` (ユーザー PDS) |
| 戦闘 | `GameState.jobXp` (サーバー権威) |
| 依頼クエスト | 完了集合からの派生 (どこにも保存されない) |

これが「戦闘 XP がどのレベルにも効かない」(#529)、「クエスト XP が表示にしか効かない」(#533)、
「転職でレベルが失われる」(#531)、「移行で投稿 XP を種にすると二重計上」を全部生んでいた。
一本化すると出所が 1 つなので合算が不要になり、足し忘れも二重計上も構造的に起こせない。
`GameState.jobXp` は元から archetype キーなので、**職ごとのレベル保持も自動的に成立**する。

### クライアント申告の経路

投稿とクエストの XP は client が分類して算出するので、`POST /api/xp/claim` で申告する。

**信頼レベルは今より下がらない。** 旧 `analysis.jobLevel.xp` はユーザー自身の PDS にあり
client が任意の値を書けたので、偽造の天井は元から開いていた。サーバーに集約したうえで
2 つの制約を掛けるぶん、むしろ改善する:

- **上限クランプ** — 1 回の申告で入る XP を `XP_REWARDS` から導いた上限で切る。
  超過は 400 ではなく**切り捨て**。報酬定数の解釈が client と server でずれたとき、
  「正当な申告が落ちて XP が永久に入らない」より被害が小さいため
- **冪等キー** — 投稿の URI / クエストの URI をキーに、直近 200 件のリングで二重加算を防ぐ

真の偽造対策は M4 (docs/21)。

### ベータの区切り

一本化にあたり **`jobXp` を一度リセットする** (全員 Lv1 から再スタート。オーナー判断 2026-07-26)。
旧値は「移行時に焼き込んだ投稿 XP + 戦闘 XP」の混合で、そのまま持ち越すと投稿ぶんが二重に効く。

マーカーは `version` **ではなく** `GameState.xpEpoch`。`readModifyWrite` は書き込みのたびに
`version` を現在値で上書きするので片道マーカーにならず、しかも **dev と本番は同じ権威レコードを
共有している** (docs/22)。version でやると「本番 (旧コード) で 1 歩動く → 次の dev アクセスで
jobXp がまた 0」という往復ワイプが起きる。`xpEpoch` は旧コードが知らないフィールドだが
`{...cur}` のスプレッドで保存されるので、一度書けば残る。

過去の到達レベルは `analysis.jobLevel.xp` に**凍結して残し**、`/me` に
「ベータ期間の記録」として表示する。**この値はもうどの経路からも書き換えない** —
投稿処理も、転職 (`confirmJobChange`) も、管理者のジョブ変更 (`adminSetJob`) も触らない
(上書きすると PDS ごと消えて復元できない)。

区切りでは **位置も spawn に戻す**。Lv1 にしたのに立ち位置が奥地のままだと、想定 Lv8 以上の
敵に Lv1 で遭遇し、負けるたびに素材を失う死にループに入る (帰還先の `lastTown` もその地方なので
抜け出せない)。持ち物・パワー・装備は触らない — XP 以外を巻き添えにしない。

リセットしたことは、**実際にレベルを失った人にだけ**一度だけ知らせる (`BetaResetNotice`)。
何の説明も無いと「LV30 → LV1」だけが見え、通信障害と本物のリセットが見分けられない。

### 「まだ分からない」を 0 に丸めない

LV を表示する画面は権威 state を読むが、**取得できていないあいだは LV を出さない**
(`xpOfJob` は `number | null` を返す)。0 に丸めると通信断が「レベルが戻された」に見え、
このリリースでは本物のリセットと区別がつかなくなる。

### 管理者のジョブ変更

一本化の結果、`analysis` を書き換えるだけではレベルが動かなくなった。Lv30 パッシブ等の
実プレイ確認は開発に必要なので、`POST /api/xp/admin-set` (ADMIN_DIDS ゲート) を用意して
**その職の曲線から**指定レベルちょうどの XP をセットする。基準曲線で引くと、pace が
1 未満の職では指定より高いレベルになる (「Lv30 を確かめたいのに Lv34」)。

## 6.4.7 tier とモンスターの想定レベル (#536)

### tier は 8 段階

`Tier = 1..8`。**3 段階では敵の強さと XP が 3 バケツに丸まる**ため広げた。DQ3 は
序盤 4 XP → 中盤 35 → 終盤 12200 と連続的に伸びるのに、3 段階だと tier1 内 (2〜7 XP) と
tier2 内 (34〜52) の間に断絶ができ、「同じエリアなのに全部同じ強さ」になっていた。

`regionDanger` も 0..3 → **0..7** に広げた。spawn からの距離は元々 0..8 の解像度があったのに、
0..3 に潰して捨てていた。

| tier | 想定 Lv | 位置づけ |
|---|---|---|
| 1〜2 | 1 / 4 | 入口 (はじまりの街の周辺) |
| 3〜4 | 8 / 13 | 中盤 |
| 5〜6 | 19 / 26 | 奥地 |
| **7** | 34 | **魔王の城がある山あい** (枠のみ。下記) |
| **8** | 42 | **城の内部** (枠のみ。城の実装待ち) |

**遭遇に使うのは `MAX_POPULATED_TIER` まで**。これは「顔ぶれが 3 体以上いる最大の tier」を
敵の表から自動で求めた値で、現在は **3**。tier を先に 8 段階へ広げても敵は後から足すので、
その間は

- プールが空の帯 → `summonMonster` が `undefined` を返し move が 500 になる
- プールが 1〜2 体の帯 → 毎回同じ敵しか出ず、地域相性のヒントも常に同じ名前になる

という壊れ方をする。敵を 3 体足すごとに上の帯が自動的に解放される。

### 上限で切るのではなく、帯を引き伸ばす

`tierForDanger` は danger をそのまま tier にして上限で切る**のではなく**、
`1 + round(max(0, danger − 2) × (最大 tier − 1) / 5)` で帯を引き伸ばす。

上限で切ると、**敵が足りないぶんが全部いちばん上の帯に詰まる**。実際にそれをやったとき:

| | 入口 (tier1) | 中間 (tier2) | 最上 (tier3) |
|---|---|---|---|
| 上限で切る | 7 リージョン / 6 街 | 10 / 9 | **47 / 38** |
| **引き伸ばす (現在)** | **32 リージョン / 24 街** | 24 / 22 | 8 / 7 |
| 参考: tier 3 段階だった頃 | 30 / 23 | 26 / 23 | 8 / 7 |

上限で切ると spawn から 3 リージョン歩けば想定 Lv8 の帯で、世界の 73% が同じ 3 体になる。
「入口が一番大事」に真っ向から反する。引き伸ばしなら**敵を足しても世界の形は変わらず、
傾斜が細かくなるだけ**で済む。

danger 0..2 を一律 tier1 にするのは、spawn 周辺に「ノイズで急に強くなる」場所を作らないため
(jitter が 0.9 あるので距離 2 までは揺れで前後する)。

### 敵ごとの想定レベル

`MonsterDef.level` で敵ごとに想定プレイヤーレベルを持たせる (省略時は tier の代表値)。
**同じ tier の中にも「弱い敵/強い敵」の階段**ができる (そらいろスライム Lv1 →
ほらあなコウモリ Lv3 のように)。tier は「どのエリアに出るか」の括りで、
強さと XP はこの値で決まる。

### 魔王の城がある山あい (tier7) — 場所だけ確保、適用は保留

リージョン (4,4) と (5,4) (左上を (1,1) とする) を `DEMON_CASTLE_REGIONS` として記録する。
将来ここを**距離を無視して tier7** にする (`tierForRegion`)。

**ただし今は適用しない。** 地形を実測したところ、閉じた最果てではなかった:

| | 歩行可能率 | 街 | tier1/tier2 との接触 |
|---|---|---|---|
| (4,4) | 52% | なし | 109 タイル |
| (5,4) | 26% | **おおたきの宿** | 49 タイル |

(接触タイル数 = 4 近傍で、歩行可能タイル同士が帯をまたいで隣り合う数)

このまま tier7 を強制すると (a) Lv5 のプレイヤーが 1 歩で想定 Lv34 の帯に入れてしまい、
(b) 城が未実装で tier7 の敵が 0 体なので、街「おおたきの宿」から出た瞬間に move が
500 になって**その街から出られなくなる**。

適用の条件は 2 つ: **城を実装して tier7/tier8 の敵を置くこと**と、
**そこへ至る段階 (tier5→6) を配置して、入口から地続きで入れないようにすること**。

### 敵の魔法は tier2 から

**魔法 (`useInt`) は回避判定を通らない** (`doAttack` の `if (!opts.useInt)`)。
回避特化 (忍者) が一方的に無傷で勝ち続けるのを止める役として、`ability: 'caster'` の敵を置く。

**入口 (tier1) には置かない** — tier2 から回避が通用しなくなる = 先へ進むほど別の備えが
要る、という学びの山にする。実測: 忍者は tier1 で 42 連戦できるが tier2 では 4.1 連戦。

### 敵の XP は DQ3 に合わせる

**tier1〜6 の敵は `xp` を全て明示する。** `baselineXp` の式は HP と atk/agi から
XP を出すが、HP の重い敵と軽い敵が tier をまたいで並ぶと **tier2 の敵 (6) が
tier1 の敵 (7) を下回る逆転**が起きた。式は「xp を書き忘れて敵を足したとき」の
保険として残す。

| 帯 | 我々 | DQ3 |
|---|---|---|
| tier1 (想定 Lv1〜3) | 3 / 4 / 5 / 6 / 8 / 9 | スライム4 / おおがらす6 / いっかくうさぎ8 |
| tier2 (想定 Lv4〜7) | 12 / 14 / 15 / 18 / 19 / 21 | おおありくい12 / まほうつかい18 |
| tier3 (想定 Lv8〜12) | 28 / 34 / 42 | キャタピラー35 / ぐんたいガニ35 |
| はぐれスライム | 100 (ジャックポット) | メタルスライム 4140 |

### 職ごとのレベル曲線

DQ3 も職業ごとに必要経験値が違う (Lv99 で勇者 630 万 対 賢者 960 万 = 1.5 倍)。
さらに **Lv10 で 2.5 倍 → Lv50 で 1.46 倍と収束**する。同じ形にした:

- `JOB_LEVEL_PACE` — **持久力の実測値から導く**。強い職ほど大きい = 上がりにくい
- `JOB_LEVEL_PACE_DECAY` — 後半で職差を薄める。序盤 1.60 倍 → Lv50 で 1.22 倍に収束

「序盤は職の個性が強く出て、終盤は皆が同じ地平に立つ」形。定数倍だと後半も開いたままで、
強い職がいつまでも追いつけない。

`JOB_LEVEL_PACE` の値は手で決めず、下の連戦計測を最小値で正規化して **0.35 乗**し、最大を 1.0 に揃えたもの。
持久力の開き 6.81 倍 (mage 4.2 戦 対 shogun 28.6 戦) をそのまま必要 XP に反映すると
弱い職が育ちすぎて逆に追い越すので、**1.96 倍まで圧縮**している。
導出は 測定 → テーブル → 測定 の不動点探索で、単純反復だと 2 周期で振動するため緩和係数 0.5 を掛ける。
導出元の連戦数は `JOB_LEVEL_PACE_BASIS` としてデータで持ち、順序の一致をテストで固定する。
計測条件を変えたら (敵の強さを触ったら) この値も引き直す。

## 6.5 戦闘の強度モデル (固定強度 — オーナー要望 2026-07-20)

**敵はプレイヤー/ジョブレベルに追従しない = tier (エリア) 固定強度**。
「自分の強さに合わせて敵も強くなるのはダメ (やるとしても終盤エンドコンテンツ)」。

- `monsterLevelFactor(def)` は敵の想定レベルと tier のみ (#536)。旧実装にあった playerLevel/jobLevel 追従と、
  モンスターへの `flatLevelGain` 加算は**撤廃**した。
- **tier = そのエリアの「想定プレイヤーレベル」** (`TIER_LEVEL = {1:1, 2:10, 3:20}`、#518)。
  モンスターの `stats` は職と同じ**合計 100 の比率**なので、プレイヤーと同じ成長式
  `statFloor + 比率 × (statBase + statGrow × (Lv−1))` に載せないとスケールが噛み合わない。
  tier をレベルで表すことで、プレイヤーの成長レンジ (Lv1→30 で約 8 倍) と同じ幅を tier 側も
  持てる。**これは「敵がプレイヤーに追従する」ことではない** — tier はエリアに固定で、
  プレイヤーが伸びれば既存エリアが楽になる性質は変わらない。
- `MONSTER_POWER = 0.5`: モンスターの profile は utility (int/luk) に予算を割く必要がない
  ぶん atk に偏る (あおおには 126 中 66 = 52%、戦士は 100 中 25 = 25%)。同じ倍率で並べると
  殴り合いが 2 ターンで終わる大味な戦闘になるため、profile の形は保ったまま出力だけを
  職と同水準に均す。
- モンスターの HP も `hpBase + hp × 成長率 × hpVitScale` に載せる (`hp` を職の vit と同じ
  「たいりょく相当の生値」として扱う)。旧実装は `hp` をそのまま絶対 HP にしていたので
  tier2 (22〜28) → tier3 (24〜30) とほぼ伸びず、上位 tier ほど瞬殺されていた。
- 同じ敵は Lv1 でも Lv30 でも強さが同一 (HP/atk/def/agi/int/luk/MP)。プレイヤーが伸びれば
  既存エリアは**相対的に楽になる** = 成長が報われる。
- **後半の難易度は「レベル追従」ではなく「エリアごとに強い敵を配置」で作る** (出現セット/
  エリア設計は後続 PR)。終盤エンドコンテンツで追従を戻すなら tier 限定で `monsterLevelFactor`
  に足す。
- **撤廃した旧監視項目** (docs/18 に記載があった「高 Lv で tier3 が作業化しないよう追従で
  釣り合いを取る」「tier3 天井 <94%」等) は、固定強度では**意図的に不採用**。outleveling で
  楽になるのが正しい挙動。

**過渡期リスク (エリア設計 PR が入るまで)**: tier2/3 も固定強度なので、レベルを上げると
全 tier が楽になる (sim: plLv20 で tier1/2/3 とも 5 連戦生存 ~100%)。逆に低レベルで高 tier に
入ると即死 (plLv1×tier3 = 0%)。後半エリアの再ハード化 (強い敵の配置) と、アンチファーム
(強くなると弱い敵は逃げる / XP カーブ) を後続で積んで回収する。危険領域の視認性・進入警告は
別 issue。

## 6.6 入口の難易度は「街を出てから何戦もつか」で測る

勝率ではなく**連戦数**を指標にする。街は全回復地点で、HP・MP・やくそうは戦闘をまたいで
持ち越し、瀕死なら野外でやくそうを飲む。「1 戦の勝率 90%」でも回復が尽きれば 3 戦で
死ぬので、勝率だけ見ていると入口の体感を取り違える。

計測: tier1 / Lv1 / 装備なし / 全 16 職 × 30 試行 / `runAutoBattle`。

| | tier1 Lv1 裸 | tier2 Lv5 布の服 | tier3 Lv9 旅の外套 |
|---|---|---|---|
| `monsterStatFloor` 6 | 2.25 戦 | — | — |
| **3 (採用)** | **7.24 戦** | 17.81 戦 | 7.87 戦 |

再現: `pnpm --filter @aozoraquest/core sim:endurance` (`TIER` / `LV` / `GEAR` で条件を変える)。
**スクリプトが repo に無いと引き直せない**ので、`scripts/sim-endurance.mts` に置いてある。

## 8. 判断ログ (2026-07-17 オーナー回答)

1. **移動コスト**: 1 歩 = 1 パワー厳守 (ヘビーユーザーは 1 日 100 投稿 = 100 歩)。
2. **敗北**: 最寄りの街戻りのみ。
3. **店**: 街ごとに品揃えが違う。地域モンスターに効く (特効) 装備を売る。
4. **街に固有名を付ける** (§3)。
5. **Durable Objects の課金試算** (2026-07 時点の CF 料金で):
   - DO は **Workers Free プランでも利用可** (SQLite-backed)。無料枠は
     リクエスト ~300 万/月・compute 約 39 万 GB 秒/月・ストレージ 5GB
     (Free プランはストレージ課金なし)。
   - 本機能の負荷: 1 歩 = 1 パワー = 1 投稿相当なので、ヘビーユーザーでも
     ~100 歩/日 = 100 リクエスト/日/人。戦闘もサーバー解決 (1 ターン 1 リクエスト)
     で、遭遇 ~10 戦/日 × ~10 ターン = +100 リクエスト/日/人。**合計 ~200/日/人**。
     アクティブ 100 人でも 2 万 req/日 ≈ 60 万/月 = **無料枠 (~300 万/月) の 20%**。
     DO はハイバネーションで待機中は compute 課金されず、保持するのはカウンタ +
     座標 + 進行中 BattleState (~1KB)。
   - **結論: 想定規模では追加課金 $0** (無料枠内)。有料プラン ($5/月) でも
     込み枠が桁違いに大きく増額なし。アカウントのプラン種別だけ実装時に確認する。

## 6.7 地形は「1 タイル 1 バイトの地図」で持つ (#421)

地形は `baseTerrainAt` が 1024×1024 をノイズから毎回計算していた。マップエディタで
手編集するには差分を持つしかないが、**疎な差分は上限が要り**「広い面積を塗ると
保存できない」「上限超過で断る」「部分適用しない」という問題を丸ごと抱える。

**画像として持てば塗り放題で、しかも小さい** (実測):

| | 値 |
|---|---|
| 生バイト (1 タイル 1 バイト) | 1,024 KB |
| gzip 圧縮後 | **27.2 KB** |
| gzip 展開 | 0.6 ms |
| 読み込み全体 (base64 → 展開 → 配列) | 8 ms |

副産物として**速くなる**。`terrainAt` はノイズ計算 3.27 µs/回 に対し、地図があれば
**0.060 µs/回** (約 55 倍)。全域スキャン 3.3 秒が不要になり、edge の CPU 時間にも効く。

```
terrainAt = 地図 (画像) ?? overlay (街/橋) ?? base (ノイズ生成)
```

### 決めごと

- **パレットは 1 バイト = 256 種**。地形は増える前提なので 8 種に固定しない。
  index → 地形 id はデータとして持ち運ぶ
- **知らない index / 知らない地形 id は `fallback` に倒す**。エディタで新地形を足した
  瞬間、まだデプロイされていない edge / web がそれを読むタイミングが必ずある。
  そこで落ちたり通行判定が狂うと**プレイヤーがその場から動けなくなる**
- **既知の 8 種は index 0〜7 に固定。並びを変えない** (変えると既存地図が全部ずれる)
- **保存形式は PNG ではなく生バイトの gzip**。Cloudflare Workers に PNG デコーダが無く、
  gzip は `DecompressionStream` が標準で使えて依存ゼロのため。
  外部の絵描きツールで描きたい場合は**エディタ側だけ** PNG 入出力に対応させる
- **パレットは色も持つ** (`TERRAIN_COLORS`)。地形を増やすと必ず「パーツ (タイルの絵) が
  要る」問題が出るが、絵が揃うまで編集を始められないのは困る。**色だけ決めれば
  地図もエディタも動く**ようにしてある。絵は後から差し替える
- 同梱の地図 (`pnpm gen:world` が生成) は**ノイズ生成の結果そのまま**なので、
  読み込んでも見た目は 1 ピクセルも変わらない (実測: 5,000 地点で差分 0)
- **読み込むまでは従来のノイズ生成に倒れる**ので、待たずに遊べて結果も一致する

### 残っていること

- 編集した地図を管理者 PDS に保存し、**edge が読む**配線 (移動判定は edge が権威なので、
  web だけに置くと「画面では歩けるのにサーバーが弾く」= その場から動けなくなる)
- 保存前の到達性検証 (§1 の「spawn から歩行可能タイルの 95% 以上に到達できる」保証)
- 街の編集 (追加・移動・削除)。**街を 1 タイル動かすと店の品揃えが全部変わる**
  (`townShopStock` は街の x/y をシードにした純関数) ので、エディタ側で明示する

### タイルの絵はドット絵をデータで持つ

タイルの見た目は `world-tiles.tsx` の SVG を**コードに直書き**していた。地形は 256 種まで
増える前提なので、増やすたびにコードを書くのは続かない。**エディタで描いたドット絵を
データとして持つ**ようにした (`tile-art.ts`)。

- 1 タイル = `size × size` の画素で、各画素は**タイル内パレットの索引 1 バイト**。
  **色そのものを画素に持たない**のは、パレットを差し替えるだけで夜・雪・毒沼のような
  色調を、絵を描き直さずに出せるようにするため
- 16×16 なら 1 地形 ~370 バイト。**256 地形ぜんぶ描いても ~93 KB**
- 描画は **ドット絵 → 従来の SVG → 代表色のべた塗り** の 3 段で倒れる。
  地形を増やすと必ず「絵がまだ無い」状態を通るので、そこで描画が止まらないようにする
- 画素は `<rect>` の並びで出すが、**同じ色が続く区間は 1 本にまとめる**

`/admin` に「タイルのドット絵」エディタがある (パレット / 塗り / JSON 入出力)。
新規作成はその地形の代表色でべた塗りした状態から始まる (真っ白から描き始めない)。
